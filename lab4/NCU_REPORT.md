## 2. Разбор каждой реализации для преподавателя

### А. Наивная версия из Главы 6 (`matrixMult_naive`)
* **Суть работы:** Каждая нить считает ровно один элемент результирующей матрицы $C[i, j] = \sum_{k=0}^{N-1} A[i, k] \cdot B[k, j]$.
* **Почему медленно:** Чтобы вычислить одну скалярную сумму, нить делает $2N$ обращений в память. Нити соседних строк заново читают одни и те же элементы матрицы $B$ из медленной памяти (L2/DRAM).
* **Показатели NCU:**
  * Занимает 52 регистра на нить.
  * Shared Memory не используется (0 байт).
  * Тратит **671 857 тактов** GPU на выполнение.

### Б. Версия с Shared Memory из Главы 7 (`matrixMult_shared`)
* **Суть работы:** Матрицы делятся на тайлы размером $16 \times 16$. Блок нитей ($16 \times 16 = 256$ нитей) синхронно загружает один тайл матрицы $A$ и один тайл матрицы $B$ в разделяемую память (`__shared__ float As[16][16], Bs[16][16]`), синхронизируется через `__syncthreads()`, перемножает их в быстрой Shared Memory, снова синхронизируется и переходит к следующему тайлу.
* **Почему быстрее:** Каждое значение из глобальной памяти читается блоком нитей **всего 1 раз вместо 16 раз**! Повторные чтения происходят из ультрабыстрой Shared Memory (латентность ~20-30 тактов вместо ~200-400 тактов глобальной памяти).
* **Показатели NCU:**
  * Время снизилось с 1.15 мс до **0.76 мс** (ускорение **1.51x**).
  * Такты сократились с 671k до **445k**.
  * Расход Shared Memory: **2.05 КБ на блок** (2 массива по $16 \times 16 \times 4$ байта = 2048 байт данных).
  * Регистров на нить стало **меньше** (38 вместо 52), так как промежуточные значения хранятся в Shared Memory, разгружая регистровый файл.

### В. Библиотека cuBLAS (`cublasSgemm` $\to$ кернел `volta_sgemm_128x64_nn`)
* **Суть работы:** Промышленная реализация NVIDIA с многоуровневым тайлингом (Grid $\to$ Shared Memory $\to$ Register File $\to$ Tensor Cores/FMA).
* **Почему быстрее наивной в 8.6 раз:**
  1. **Register Tiling (Блокировка по регистрам):** Каждая нить вычисляет не 1 элемент, а подматрицу (например, $4 \times 4$ или $8 \times 8$). Это резко снижает обращения даже в Shared Memory, держа рабочие данные прямо в регистрах ALU. Поэтому регистров требуется **122 на нить**!
  2. **Большой Shared Memory буфер:** 12.54 КБ на блок против 2.05 КБ у нас. Это позволяет использовать двойную буферизацию (double buffering / prefetching), скрывая задержки памяти за счет наложения загрузки следующего тайла на вычисления текущего.
  3. **Транспонирование и доступ без конфликтов:** Память читается широкими 128-битными векторными инструкциями (`LDG.E.128` — по 4 float за такт на нить).
* **Главный вопрос от преподавателя:**
  * *Вопрос:* «Почему у cuBLAS занятость (Achieved Occupancy) всего **12.5%**, а у наивной программы — **94.7%**, но cuBLAS работает в 8.6 раз быстрее?»
  * *Ответ:* Высокая Occupancy нужна тогда, когда программе нечем занять вычислительные конвейеры во время ожидания памяти (нужно переключаться на сотни других нитей). cuBLAS использует **Instruction-Level Parallelism (ILP)** и держит данные прямо в регистрах (122 регистра на нить). Конвейеры ALU непрерывно заняты выполнением FMA-инструкций каждого потока, поэтому GPU не требуется держать тысячи ждущих нитей, чтобы достичь предельной производительности. Occupancy — это инструмент сокрытия задержек, а не показатель пиковой скорости.

## 3. Ответы на контрольные вопросы по защите ЛР4

1. **Почему `ncu` выдал ошибку на кластере (`ERR_NVGPUCTRPERM`), и как вы его запустили?**
   * *Ответ:* В современных ядрах Linux доступ к низкоуровневым аппаратным счетчикам производительности GPU по умолчанию закрыт для непривилегированных пользователей из соображений безопасности (параметр ядра `NVreg_RestrictProfilingToAdminUsers=1`). Так как на университетском кластере нет прав `sudo`, профилирование ядра было выполнено на виртуальной машине Google Colab с GPU Tesla T4 с правами суперпользователя.

2. **Есть ли конфликт банков (Bank Conflicts) в вашей реализации с Shared Memory?**
   * *Ответ:* В архитектуре NVIDIA Shared Memory разбита на 32 банка по 4 байта.
     * При чтении из `As[threadIdx.y][k]`: все нити одного варпа с одинаковым `y` обращаются к **одному и тому же адресу** `As[y][k]`. В CUDA это вызывает **Broadcast** (широковещательную рассылку) — один банк рассылает данные всем нитям варпа за 1 такт без конфликтов!
     * При чтении из `Bs[k][threadIdx.x]`: нить $x$ читает банк $(k \times 16 + x) \pmod{32} = x \pmod{32}$. Все 16 нитей полуварпа обращаются к разным банкам ($0 \dots 15$), конфликтов банков нет.

3. **Зачем нужна инструкция `__syncthreads()` дважды в цикле?**
   * *Ответ:*
     1. Первый `__syncthreads()` гарантирует, что все 256 нитей блока закончили загрузку текущего тайла из глобальной памяти в `As` и `Bs`, прежде чем хоть одна нить начнет перемножение.
     2. Второй `__syncthreads()` гарантирует, что все нити закончили вычисления над текущим тайлом, прежде чем нити следующей итерации перезапишут массивы `As` и `Bs` новыми данными.

4. **Что происходит при росте размера матриц до $2048 \times 2048$ (эффект L2 кэша)?**
   * *Ответ:* Матрицы $512 \times 512$ ($1$ МБ) и $1024 \times 1024$ ($4$ МБ) целиком или частично помещаются в L2-кэш GPU (например, 6 МБ на Tesla V100). При размере $2048 \times 2048$ две входные матрицы занимают $2 \times 16 = 32$ МБ, что полностью вытесняет L2-кэш. В результате наивная версия начинает непрерывно считывать данные из медленной DRAM-памяти, и производительность падает до 600 GFLOPS, в то время как cuBLAS сохраняет свыше 13 000 GFLOPS благодаря глубокому многоуровневому кэш-блокированию.
